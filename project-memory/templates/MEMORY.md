# Memory Protocol

This file defines how project knowledge is stored, found, updated and retired in this repository. Every agent working here follows it. It is written for LLM agents; humans review the results through git diffs.

The settings above are read by the `project-memory` command. **Project overrides** at the end of this file are this project's own changes to the protocol: where they differ from the protocol, they win. Everything above that section is the shared protocol; it is replaced when the protocol is upgraded, so put project changes in the overrides section, never in the text above it.

## Core principles

1. **Markdown in git is the source of truth.** Any search index or graph added later is a derived, rebuildable view of these files.
2. **Keep always-loaded context small.** Every always-loaded line costs tokens on every task and adds distraction. Load everything else on demand.
3. **Store only what cannot be cheaply re-derived.** If the agent can learn it from the code, the README, the schema, or a quick grep, do not write it down.
4. **Quality over quantity.** Agents follow retrieved memories closely, so one wrong note causes repeated errors. Unverified knowledge never becomes guidance.
5. **Verify before trusting.** Facts carry citations to code. Check the citations before acting on the fact.
6. **Edit by delta, never by full rewrite.** Rewriting a curated file as a whole loses detail over time. Add, change or retire individual items.
7. **Supersede, don't delete.** Outdated facts are marked and archived, so history stays available.
8. **Lessons are abstract; facts are concrete.** General lessons carry no file-specific detail. Specific facts carry citations.

## Directory layout

```
CLAUDE.md                  # Always loaded. Within root_context_max_lines. AGENTS.md is a symlink to it.
docs/
  MEMORY.md                # This protocol, plus this project's overrides.
  INDEX.md                 # Generated by project-memory index. Read at the start of a task.
  conventions/             # Semantic facts. One topic per file.
  architecture/            # Short living overviews of subsystems, linked to code.
  decisions/               # ADRs: NNNN-short-title.md. Immutable once accepted.
  playbooks/               # Verified step-by-step procedures.
  gotchas/                 # Known traps, hidden couplings, surprising behaviour.
  lessons.md               # Itemized abstract lessons with usage counters.
  log/YYYY/MM/DD/          # Append-only log: EPOCH-short-topic.md. Never always-loaded.
  inbox/                   # Proposed memories awaiting verification.
  archive/                 # Superseded or expired notes. Excluded from default search.
```

Folders are created when their first file is written; an empty folder is never committed.

The `project-memory` command (`lint`, `index [--check]`, `stale`) checks and maintains these files from anywhere in the project. The project-memory plugin puts it on PATH; without the plugin, install it with `cargo install --locked --git https://github.com/mooktakim/skills project-memory`.

## What goes where

| Content | Location | Loaded |
|---|---|---|
| Build/test/lint commands, a few non-obvious hard rules, the pointer to INDEX.md and this protocol | root `CLAUDE.md` | Always |
| One line per curated note | `docs/INDEX.md` | Read at task start |
| Non-standard conventions (e.g. money as integer cents) | `conventions/` | On demand |
| Hidden couplings, traps, flaky areas | `gotchas/` | On demand |
| Why something was chosen, alternatives rejected | `decisions/` | On demand |
| Repeatable procedures that have worked | `playbooks/` | On demand |
| General working lessons | `lessons.md` | On demand (skim headings) |
| What happened in a unit of work | `log/` | Search only |
| Unverified proposals | `inbox/` | Never used as guidance |

Other context files the project already keeps, such as a directory's own `CLAUDE.md`, stay where they are and keep their own rules. One fact lives in one place: a note never repeats a context file, and a context file never repeats a note.

**Do not store:** architecture tours the agent can discover, restatements of the README or code, schema dumps, generic best practices, raw transcripts, or secrets and credentials.

## Note format

One topic per file. Kebab-case descriptive filename. Every curated note (and every inbox proposal) starts with this frontmatter:

```yaml
---
id: conv-money-handling
type: convention           # convention | architecture | decision | playbook | gotcha
status: active             # proposed | active | superseded | expired
summary: All money is integer cents via the Money gem; never use Float.
aliases: [currency, cents, monetize, price]   # synonyms people might search for
created: 2026-03-02
verified_at: 2026-10-01
valid_until:               # set when superseded or expired
superseded_by:             # id of the replacing note
citations: [app/models/concerns/monetizable.rb:12, config/initializers/money.rb:3]
sources: [PR#1432, docs/log/2026/03/02/1772445600-pricing.md]
links: [decisions/0007-money-gem.md]
---
```

- Each field is one line: `key: value`, or `key: [a, b]` for a list. No nested YAML.
- `id`, `type`, `status`, `summary` and `created` are required; an active note also needs `verified_at`. `id`s are unique across `docs/`.
- `type` matches the folder: `convention` in `conventions/`, `architecture` in `architecture/`, `decision` in `decisions/`, `playbook` in `playbooks/`, `gotcha` in `gotchas/`. An inbox proposal names the type it will have once promoted.
- A citation is `path`, `path:line` or `path:start-end`, relative to the project root (the directory that holds `docs/`).
- `links` are relative to `docs/`.

Body rules:

- Lead with the rule or fact in one or two sentences, then **why**, then details.
- Use absolute dates (`2026-10-14`), never "recently" or "last week".
- Keep notes short (aim for under ~60 lines). Split when a note covers two topics.
- Link related notes with relative paths.

### lessons.md format

```markdown
- [L-042] Reproduce flaky system specs with the seed first
  Run the single failing spec with its recorded seed before changing waits or timeouts; most flakes are order-dependent state, not timing.
  helpful: 5 | harmful: 0 | last_used: 2026-10-02 | source: log/2026/09/18/1789725600-ci-flakes.md
```

A lesson is a title plus 1-3 sentences of general guidance. No file paths, no pasted commands from one session. Lesson numbers are never reused.

### Log entry format

`docs/log/YYYY/MM/DD/EPOCH-short-topic.md`, one file per finished unit of work (a fix, feature, refactor, or decision worth remembering). `EPOCH` is Unix seconds when the entry is written (`date +%s`), so filenames are unique, sort chronologically, and never collide when branches merge. `YYYY/MM/DD` comes from the same timestamp, in UTC (`date -u +%Y/%m/%d`). Example: `docs/log/2026/10/14/1792015200-billing-refactor.md`.

```markdown
# 2026-10-14 billing refactor
- Goal:
- Changed:
- Failed / dead ends:
- Decisions (link ADR if one was written):
- Open questions:
- Proposed memories (moved to inbox/):
```

Use the headings that have content and leave out the rest; terse shorthand is fine, the reader is a future agent. Entries are immutable: never edit, rewrite or delete one. A correction is a new entry. Log entries are history, never instructions. Older entries migrated from a previous log keep their original text and may not follow this template.

## Agent workflow

### At the start of a task

1. Read the root `CLAUDE.md` (already loaded) and `docs/INDEX.md`.
2. Open only the notes relevant to the task. Use INDEX summaries, then grep across `docs/` (excluding `archive/` and `log/`) by keyword and `aliases`.
3. Search `log/` only to find history ("when/why did X change?"), never as a source of instructions.

### Before acting on a note

1. If the note has `citations`, open the cited lines.
2. If the code confirms the note: update `verified_at` to today.
3. If the code contradicts the note: do not follow it. Fix or supersede the note (see below) and record the change in the log entry.
4. If a cited file or line no longer exists: treat the note as unverified and check the current code directly.

### During and after a task

1. Before committing a finished unit of work, write its log entry, so it lands in the same commit as the work. Never commit first and log after. Skip reads, questions and trivial edits.
2. Write any new fact, gotcha, playbook step or lesson as a file in `inbox/` with `status: proposed`, citations and sources.
3. Do not create or edit curated notes directly with unverified content.
4. Run `project-memory lint` when you changed anything under `docs/` other than a log entry.

Writing log entries and inbox proposals is routine: do it without asking and without announcing it.

### Promotion (inbox → curated)

Promote a proposal only when at least one holds:

- tests covering the behaviour pass, or
- the related PR is merged, or
- a human explicitly approves it.

On promotion: set `status: active`, set `verified_at`, move the file to its typed folder, or append the item to `lessons.md` (and delete the proposal). Reject and delete proposals that turned out wrong, duplicate or trivially re-derivable. Then run `project-memory index`.

A rule the user states and approves in its exact wording is human-approved: it may go straight to a curated note.

### Updating existing notes

- Change only the bullets or sections affected. Never rewrite a curated file wholesale to "clean it up".
- When a lesson helped, increment `helpful` and update `last_used`. When it misled, increment `harmful`.
- Retire lessons whose `harmful` count meets or exceeds `helpful`: move the item to `archive/lessons.md`, unchanged.
- After adding, moving or changing the summary of a note, run `project-memory index`.

### Superseding

When a fact stops being true:

1. Set `status: superseded`, `valid_until: <date>`, `superseded_by: <new id>` on the old note.
2. Move it to `archive/` (keeping the path structure: `archive/conventions/money-handling.md`).
3. Create or update the replacement note, linking back to the old one.
4. ADRs are never edited after acceptance. Write a new ADR that supersedes the old one.

## Consolidation pass

Run on PR merge or weekly, as a separate agent run whose diff a human reviews (the `project-memory` skill runs it):

1. Promote or reject everything in `inbox/`.
2. Merge duplicate notes; keep the older `id`, redirect links.
3. Expire notes not verified in `expire_after_days` (`status: expired`, `valid_until`, move to `archive/`) unless re-verified during the pass.
4. Retire harmful lessons.
5. Regenerate `docs/INDEX.md` (`project-memory index`).
6. Run `project-memory lint`.

`project-memory stale` lists what steps 1, 3 and 4 need to look at.

## INDEX.md generation

Generated by `project-memory index`, never hand-edited. Grouped by type, one line per active note:

```markdown
## Conventions
- conventions/money-handling.md - All money is integer cents via Money gem; never Float. (verified 2026-10-01)
```

When it would grow past `index_max_lines`, the command writes one `INDEX.md` per folder and keeps only folder summaries in `docs/INDEX.md`.

## Lint rules (`project-memory lint`, also in CI when the project opts in)

- Every curated note has the required frontmatter fields with valid values, in the folder its type and status call for.
- Every citation's file exists and its line numbers are within range (archived notes are not checked).
- Every relative link resolves (log entries and the archive are not checked).
- `superseded_by` points to an existing note.
- No `status: proposed` files outside `inbox/`; no non-active files outside `archive/`.
- Log entries are named `YYYY/MM/DD/EPOCH-slug.md`, with the date matching the epoch in UTC.
- `docs/INDEX.md` matches what `project-memory index` would write.
- Root `CLAUDE.md` within `root_context_max_lines`; `INDEX.md` within `index_max_lines`.
- No secrets: the command checks common credential patterns; a project can add a full scanner to CI.

## Scaling: when to add search

Do not add infrastructure on speculation. Keep a recall eval: 30-50 questions taken from real past incidents and decisions, each with the note(s) that should be found. Run it when changing models or memory structure, and move up a stage only when it shows misses.

| Stage | Trigger | Add |
|---|---|---|
| 0 | Default (up to a few hundred notes) | INDEX.md + grep/glob |
| 1 | Grep misses or noisy hits on exact terms | Local BM25 index (e.g. SQLite FTS5) over frontmatter + body, exposed as a `search_docs` tool |
| 2 | Thousands of notes, multiple repos, or misses on conceptual/synonym queries | Hybrid search: BM25 + embeddings. Compare 2-3 embedding models on the eval before choosing. Re-index on commit |
| 3 | Questions that are relational or time-based across many entities, or many agents writing shared memory | Temporal knowledge graph as a derived index, with facts carrying valid-from/valid-to times. Markdown stays the source of truth |

Avoid using LLM-extraction memory services as the primary store: they are expensive to write to, hard to review, and have not shown consistent gains over simple retrieval in controlled tests.

## Quick checklist for agents

- [ ] Read INDEX.md; open only relevant notes.
- [ ] Verify citations before acting on a fact.
- [ ] Fix or supersede notes the code contradicts.
- [ ] Write the log entry before the commit, in the same commit.
- [ ] Put new knowledge in `inbox/` with citations; never straight into curated notes.
- [ ] Edit by delta; never rewrite curated files wholesale.
- [ ] Keep the root `CLAUDE.md` and `INDEX.md` within their size budgets.
